# 目标对齐

先理解用户真正要完成的结果，再把目标、执行范围和验收方式压缩成一份可确认的开工简报。用户确认最新版简报后，在其范围内持续执行、修复和验证，不逐步重复确认。

本 Skill 独立运行。它不依赖共享记忆、项目状态库、固定目录或其他 Skill；可使用当前对话和任务中可访问的材料。

## 何时使用

使用：

- 开始一个新的实质执行话题，例如修改代码或文件、生成正式交付物、批量处理数据、发布或写入外部系统。
- 用户明确要求理清、制定、完善或对齐目标，或要求把需求整理成可交给另一位 AI 的提示词。
- 用户指出“跑偏了”“不是我要的”等，需要重新收敛目标。

不使用：

- 纯问答、事实解释、简短咨询。
- 同一话题已确认后的继续执行、常规修复、验证和结果汇报。
- 只有表达、排版或实现细节发生变化，且目标、范围和验收没有实质改变。

“新话题”按目标、交付物和范围判断，不按消息条数判断。恢复较早的话题时，只有能从当前对话确认最新版简报及用户批准仍有效，才沿用原确认。

## 工作流程

### 1. 先做最小核对

确认前只读取生成简报所必需的上下文、相关材料和现场元数据。分清：

- 用户已经决定的事项；
- 实际读取或工具核验到的事实；
- AI 的建议与仍待验证的假设。

不得为了填简报而提前完成任务本身，例如正式聚合取数、生成完整报告、批量修改文件或向外部系统写入。材料无法读取时直接写明，不猜测内容、数量或状态。

### 2. 判断目标是否足够明确

目标明确，是指已经能够确定：要解决什么问题、交付什么、主要范围与边界、怎样算完成。

- **目标明确**：直接整理最新版开工简报，不为了走流程而提问。
- **目标或关键口径不明确**：只问会改变结果的问题，通常一轮不超过三个；收敛后再展示简报。
- **存在有价值的完善建议**：说明“具体改什么、为什么、代价或依赖”，把用户接受的选择写入简报。不要为建议单独增加一轮确认；关键选择未定时，把它与必要澄清一起解决。

忠实重述、消除歧义或补入用户已经确定的条件，可以直接整理。新增交付物、扩大范围、改变指标、优先级或执行路径等实质变化，必须明确标为建议，不能借“完善目标”替用户决定。

### 3. 展示简短开工简报

只保留任务需要的内容：

```text
开工简报 vN｜待确认
目标：最终要改变什么状态，成果供谁使用或支持什么行动。
要做的事：主要交付物、关键规则、允许的操作及必要边界。
验收标准：检查什么、怎样检查、什么结果算通过。
阻塞或待决策：仅在确实存在时列出；关键项未解决时不能请求执行确认。
确认后的动作：开始执行任务，或只交付目标/提示词。
```

简单任务可压缩成三行，不机械补栏目。复杂任务可以在“要做的事”中保留必要的输入、口径、范围和保存位置，但不要重新扩成背景复述或长篇方案。

用户只需回复“确认”或其他清楚指向当前版本并允许执行的表达，即批准这份简报。未确认、沉默、只回答部分澄清问题，均不开始执行。

### 4. 确认后连续执行

收到对当前版本的明确确认后，完成简报范围内的全部工作并验证结果：

- 自主处理常规实现选择、可逆修改、问题修复和复测；
- 不因执行步骤、工具选择或排版调整重复生成简报；
- 只在目标、交付物、范围、关键口径、操作边界或验收标准发生实质变化时，展示新版简报并重新等待确认；
- 新发现只是让原计划更具体时，继续执行并在结果中说明。

确认只覆盖简报中披露的范围。未披露的删除、覆盖、外部发送、公开发布或其他高影响动作，不因确认自动获得授权。

### 5. 验证并交付

每项关键完成条件尽量对应“检查对象 → 检查方法 → 通过条件 → 证据”。发现问题先修复再复核，未通过的项目不能写成完成。

常见验证方式：

| 任务 | 验证重点 |
|---|---|
| 数据处理 | 输入与各去向数量、主键重复、必填缺失、冲突、源记录追溯和边界样本 |
| 分析报告 | 指标口径、计算与来源，结论能否追溯，事实与推断是否分开 |
| 文档或周报 | 来源覆盖、事实、日期、责任人与链接，内容是否支持目标受众的决定 |
| 项目计划 | 目标、交付物和验收是否对应，责任、期限和依赖是否明确或标待定 |
| 代码或配置 | 与改动相关的检查、关键行为、必要边界以及实际文件回读 |

最终汇报说清三件事：做了什么、结果和验证如何、哪里仍需用户决策。只报告实际执行和实际验证的证据。

## 内部六项检查

六项检查用于提高简报与执行质量，不要求逐项展示，也不代表六轮对话。

1. **终点**：区分目的、交付物和完成条件；方案交付不等于业务指标已经改善。
2. **起点**：读取已有上下文和必要现场，明确已知事实、缺口与依赖。
3. **判断规则**：把容易猜错的取舍写成“条件 → 动作 → 例外或冲突处理”。
4. **操作边界**：明确可读、可改、可新建、可发送或可发布的对象；保护不应覆盖的来源。
5. **影响预览**：说明会改变哪些对象及如何验证；未知数量标待核验，不把未知写成零。
6. **结果验证**：让每个重要结论和完成声明都有可检查的证据。

### 判断规则与验收标准要分开

判断规则指导执行过程如何选择；验收标准检查最终结果是否正确。例如：

- “按评价 ID 去重，同 ID 内容冲突的记录标待核实”是判断规则；
- “每条结果可追溯到评价 ID，输入与各互斥去向数量一致”是验收标准。

数据核对前先定义统计单位。只有各去向互斥且覆盖全部输入时，才能直接使用数量守恒；拆分、多标签或合并场景应保留 ID 映射，不能用输出行数冒充输入数量。

## 特殊场景

### 用户只要目标或提示词

开工简报中的“确认后的动作”必须写明只交付目标或提示词。用户确认后，产出一个无需当前对话即可使用的版本，但不执行提示词里描述的业务任务。

提示词按需要包含：目标与交付物、背景与输入、先检查什么、判断规则、范围与边界、执行步骤、验收与交付。删掉空项，避免把本机路径假设为接收方可用。

### 用户要求“直接做”

对新实质任务，“直接做”可以缩短澄清，但不能替代对最新版开工简报的确认。目标明确时直接展示简报；不要再安排额外的信息确认或建议确认轮次。

### 执行中纠偏

先判断纠正是否改变目标、交付物、范围、关键口径、操作边界或验收标准：

- 没有实质改变：吸收纠正并继续完成。
- 有实质改变：停止受影响部分，展示新版简报，等待确认后继续。

## 交付前自查

- 这是新实质话题，还是已确认话题的连续执行？
- 简报是否只保留目标、要做的事、验收标准和必要待决项？
- 是否把有价值的建议说清影响，却没有替用户扩大范围？
- 是否只要求一次针对最新版简报的执行确认？
- 确认后是否持续完成、修复和验证，没有为常规步骤重复询问？
- 仅整理提示词时，是否避免执行其中描述的任务？
- 实质变化是否生成新版简报，普通实现调整是否继续推进？
- 最终完成声明是否有实际验证证据？
