# 目标对齐示例

以下内容只演示流程，不代表任何真实项目的现状或规则。

## 1. 目标明确：直接给开工简报

用户：“把支付页按钮的文案改成‘确认支付’，运行相关检查。”

```text
开工简报 v1｜待确认
目标：让支付页主按钮准确表达将立即发起支付。
要做的事：把指定按钮文案改为“确认支付”，检查同一支付流程中的引用和相关测试；不改其他交互。
验收标准：目标页面显示新文案，相关检查通过，无其他文案被误改。
确认后的动作：修改、验证并交付结果。
```

用户回复“确认”后，直接完成修改、修复测试问题并复核。不要在改文件或运行检查前再次确认。

## 2. 目标模糊：先问会改变结果的问题

用户：“帮我把周报做得更有价值。”

受众和用途会直接改变内容，应先问周报供谁使用、需要支持什么决定。确认用于主管协调阻塞后，再展示：

```text
开工简报 v1｜待确认
目标：基于本周项目记录，形成供主管协调阻塞和判断交付风险的周报。
要做的事：写清本周结果、偏差影响、责任人和需协调事项；例行活动仅在影响交付时纳入。
验收标准：每项关键事实可追溯到来源，日期和责任人一致，主管能直接识别需要介入的事项。
确认后的动作：生成并验证周报。
```

用户确认后执行。不要额外增加一次“是否采纳建议”的确认。

## 3. 主动完善：建议与必要澄清一起收敛

用户：“从 App 评价里统计最多的十个问题，帮团队决定先解决什么。”

只按频次可能让轻微高频问题掩盖低频严重问题。建议补充“影响的用户任务、原文证据和待核实信息”，同时说明评价数据只能形成优先级候选，不能替团队估算研发成本。

若用户接受，简报可以写成：

```text
开工简报 v1｜待确认
目标：形成供产品团队讨论排期的十大 App 改进候选问题。
要做的事：按评价 ID 去重，统计相关评价数，并补充受影响任务、原文证据和待核实项；频次与影响证据共同支持候选顺序，不推断研发成本。
验收标准：每项问题可追溯到原始评价；去重、分类和排序规则一致；事实、推断与待核实项分开。
确认后的动作：完成分析并交付可复核结果。
```

如果用户明确只要频次清单，就尊重范围，不把未采纳的影响分析写入执行要求。

## 4. 已确认话题：连续执行

用户已经确认“修复导出失败并运行相关检查”。执行中发现一个相关测试失败，需要调整同一模块的错误处理。

这仍属于已确认目标、范围和验收，不重新展示简报。完成修复、复测并汇报证据。

如果检查发现必须修改另一项共享协议，会影响多个系统，操作边界已发生实质变化，应先展示 v2：

```text
开工简报 v2｜待确认
目标：修复导出失败，并保证共享协议的兼容性。
要做的事：除原模块外，需要修改共享协议及两个调用方；列明兼容策略和影响对象。
验收标准：原导出场景恢复，两个调用方兼容性检查通过，旧格式仍能读取。
确认后的动作：继续修改并完成回归验证。
```

## 5. 只整理目标或提示词

用户：“把刚才聊的整理成提示词，我交给另一个 AI 做。”

```text
开工简报 v1｜待确认
目标：把已确认的需求整理成另一个 AI 可独立执行的提示词。
要做的事：补齐必要背景、输入、判断规则、范围边界和验收要求；不执行提示词中的任务。
验收标准：接收方无需阅读当前对话即可知道做什么、如何判断和怎样验收；不包含未确认的假设。
确认后的动作：只交付提示词。
```

用户确认后交付提示词，到此结束。不要把“确认提示词”解释成允许执行其中的外部写入、修改或发布。

## 6. 数据处理：规则与验收分开

用户要从评价数据中提取产品问题，已提供评价 ID、用户 ID、日期和正文，并明确按评价 ID 去重。

```text
开工简报 v1｜待确认
目标：形成可供产品团队讨论的产品问题清单和可追溯分类明细。
要做的事：按评价 ID 去重；同 ID 内容冲突、无 ID 或正文缺失的记录标待核实；产品与非产品反馈分开；一条评价可对应多个问题，但每个问题内同一评价只计一次。原始文件只读，结果写入新文件。
验收标准：每个源行有明确去向；互斥去向的数量与输入一致；问题统计可追溯到评价 ID；抽查覆盖正常、重复、缺失和冲突样本。
确认后的动作：执行分类、统计、抽查和结果交付。
```

用户确认前，可以核对字段和文件结构，不提前完成全量分类。确认后完整执行；发现错分或计数问题时直接修复并复核。
