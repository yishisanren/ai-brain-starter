# 通知与裁定

## 规则

- 汇总结果写在定时任务自己的会话里：AI 应用在任务跑完时会提示，用户点开就能看，也能直接在那个会话里回复裁定。不往别的渠道发消息。
- 常规成功一句话带过。日汇总没有新的待裁定、没有失败，最终回复只写统计行和「无待裁定」。
- 周一周总结、每月 1 日月度归纳：最终回复贴「给你的一页」全文。
- 去重：`_meta/alerts.json` 记录 `类型|对象|状态` 指纹与首次时间；同指纹 7 天内不重提；未处理的待裁定只在周总结集中重提。
- 待裁定与系统异常都用五段：事项、对象是什么、判断、一句理由、可直接回复的短指令；引用 D 项 id。
- 用户不看定时任务会话也不会漏：brain-load 开工时会列出本项目待裁定，并提醒汇总多久没跑。

**项目 id 必须配一句人话解释。**用户不一定记得 `ops-dashboard-v2` 这类 id 是什么；每个出现在待裁定里的项目，都要从其 STATUS.md「目标」段取一句不超 30 字的业务说明，写成「做什么 + 当前进到哪」，不堆指标名和工具名。合并类待裁定必须两个项目都解释，并说清它们的关系（重叠 / 上下游 / 无关）。PENDING 的「内容」列就按这个写。

格式：

```
【待裁定 D-2026-09-16-01】两个数据看板是否合并
对象：
• sales-dashboard：销售总览，看各渠道成交和转化，已出数据。
• growth-dashboard：增长看板，口径刚定、还没开始取数。
判断：建议合并。
理由：同一套成交与转化指标，分开会出两个互相矛盾的状态源。
回复：D-2026-09-16-01 合并 sales-dashboard→growth-dashboard ／ 不合并
```

## 待裁定类型

| 类型 | 触发 | 用户怎么回 | 回复后你做什么 |
|---|---|---|---|
| conflict | 日汇总第四步 1-4 | `D-… 选 A` 或自由文字 | 按选择重写 STATUS；落选一方写进 history；DECISIONS 记一行 |
| merge-suggest | 新项目疑似与已有项目相同 | `合并 A→B` ／ `不合并` | 合并：按下节「合并执行」做；不合并：DECISIONS 记一行「保持独立」 |
| unsorted | 条目无项目 | `归 <id>` ／ `丢弃` | 归入对应项目并折叠；丢弃只标记不删除 |
| preference-conflict | 偏好与已确认的冲突（推断出的偏好只进「待确认」段，不登记 D 项，周总结第 7 节列出，用户同样回 `确认 P-…` ／ `作废 P-…`） | `确认 P-…` ／ `作废 P-…` | 移到「已确认」或「已作废」段 |
| skill-draft | 草案生成 | `发布 <name>` ／ `不要` | 见 skills-lifecycle.md |
| skill-failed | 同平台连续 2 次无效 | `回退` ／ `停用` ／ `<name> 在 <平台> 可用` | 见 skills-lifecycle.md |
| sensitive | 疑似密钥 | `已处理` | 标已处理；提醒用户自行轮换凭据 |
| malformed | 条目格式错误 | 修文件后 `重跑` | 下次日汇总重处理 |
| prune | 月度修剪清单 | `修剪 全部` ／ 编号 | 见 monthly.md 修剪执行 |
| rename | 周总结列出的自动创建项目 | `改名 旧→新` | 目录改名，INDEX、MAP 别名更新，旧 id 作别名 |

PENDING.md 表：`| id | 类型 | 项目 | 内容 | 选项 | 提出 | 状态 |`，id 为 `D-<日期>-<序号>`（序号全库唯一，从预处理 `ids.next.D` 起）；处理后状态写「已处理（<日期>：<结果>）」。

用户回复裁定后的通用收尾：PENDING 状态列、alerts.json 指纹加 `resolved`、相关项目 STATUS「待你裁定」段、INDEX 待裁定数、`_meta/runs/<今天>.md` 追加「裁定回写」段，最后回读一遍，回复用户改了哪些文件。

## 合并执行（merge-suggest 回复「合并 A→B」）

A 是被并入方，B 是保留方。结果必须是 B 仍然只有一套「目标 / 现状 / 下一步 …」，STATUS ≤ 60 行。

1. STATUS：**按段合并，不整份粘贴。**目标沿用 B；现状、下一步、阻塞、最近成果、已更正：取 A 与 B 的并集去重，被 B 更新的旧句删掉，同段内 A 的条目标注「（并自 A）」；待你裁定合并；最近参与按来源取最晚日期；frontmatter `sources` 合并。超过 60 行：压缩「现状」「最近成果」，细节放 history。
2. DECISIONS / HYPOTHESES / LESSONS：A 的行追加到 B 对应文件，编号与 B 重号的按预处理 `ids.next` 重编并在「来源」列注明原编号。
3. history：A 的 `history/*.md` 复制进 B 的 history，同名文件追加而不是覆盖。
4. A 目录改名 `_merged-A`（不删）；INDEX 删 A 行；MAP 别名表加 `A → B`；B 的 DECISIONS 记一行「并入 A」（来源写用户裁定 D 项）。
5. 回读 B 的 STATUS：只有一个「## 目标」、不超 60 行；不满足就重写。
6. 回写不幂等，重跑会把并入内容再追加一遍：回读时同时做精确重复检查，按「（并自」前缀、表行 id、`### L-` 块头分组，删掉完全相同的后出现行，去重后再回读计数确认。A 的条目里混着属于其他项目的假设或结论时不并入 B，注明归属，留给该项目自己的日结吸收。

## 系统异常（需要知道，不需要决策）

| 异常 | 判定 | 动作 |
|---|---|---|
| merge-failed | 日汇总写文件失败或预处理脚本报错 | 立即通知，附失败项 |
| no-inbox-3d | 连续 3 天所有机器都没有新的 inbox 文件 | 通知一次：可能 Obsidian 没开或同步断了 |
| stale-machine | 某机器最近 inbox 文件比其他机器晚 7 天以上 | 周总结第 8 节列出 |
| profile-fail | Hermes 某 profile 日结连续 3 天失败 | 周总结第 8 节列出 |
| status-truncated | STATUS 压缩后仍超过 60 行 | 通知一次，建议拆项目 |
| sync-clock | 条目时间晚于当前时间 1 小时以上 | 通知：某台机器时钟不对 |
| pending-aging | D 项超过 14 天未回复 | 周总结单列 |
| skill-drift | 物化脚本报 DRIFT：本机技能副本被直接改过 | 通知一次：把改动合回 vault，或 `--force` 丢弃 |

## 运行者

- 日汇总、周总结、月度归纳只在一台电脑的一个 AI 上跑（装大脑时选定，见仓库 `prompts/schedules.md`），避免两处同时写台账。
- 最终回复第一行写处理统计，新增待裁定按上文五段式逐项列出（项目 id 配人话解释），没有就写「无待裁定」。用户在该会话里回复裁定后，按「裁定回写」「合并执行」处理，改完回读并回复改了哪些文件。
- 汇总有没有按时跑，由 brain-load 开工时检查（`brain_watchdog.py`）：当天没有日汇总记录、上周没有周总结、上月没有月度归纳、本机某个 AI 超过 2 天没日结、STATUS 首行不对、技能副本被直接改过，都会列在开工材料最前面。
