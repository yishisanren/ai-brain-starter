# 日汇总模式（每天 02:00）

输入：`brain_merge_prep.py` 的预处理结果：`files`、`entries`、`sensitive`、`malformed`、`truncated`、`ids`。每条 entry 带 `machine`、`agent`、`project_id`（脚本按 INDEX、projects 目录、MAP 别名解析，解析不了为 null）、`project_is_new`。

### 读什么

- 运行 `brain_merge_prep.py --out auto`，它把预处理摘要落盘为 Markdown（条目全文、文件清单与 sha256、涉及项目、编号台账、STATUS 格式问题）和同名精简 JSON，只打印路径与统计。用读文件工具读这个 .md。
- 涉及项目的 STATUS / DECISIONS / HYPOTHESES / LESSONS 和全局文件（INDEX、PENDING、processed、alerts、PREFERENCES、通用 LESSONS、CORRECTIONS、经验索引、REGISTRY）直接读 brain 下的原文件；不存在的按 templates.md 新建。
- 不要为读文件写辅助脚本，不要运行任务提示词之外的命令。

- 编号全库唯一：新分配的 D / H / L / B / P 编号从 `ids.next` 给的序号开始顺序往后（格式见 `ids.format`），不同项目不能各自从 01 数起；`ids.conflicts` 里已有的重号，本次顺手把后出现的那个重编：HYPOTHESES 在「归因」列、其他台账在「来源」列注明「原编号 X，<日期> 重编」，并同步改 STATUS 里的引用。

## 第一步 预检

1. `entries` 与 `files` 都为空：照第五步第 1 条处理 `status_changes`（为空就跳过），写 `_meta/runs/<今天>.md` 一行「无新条目」，结束，不通知。
2. `sensitive` 非空：对应条目（已脱敏）追加到 `inbox/_sensitive/<今天>.md`，登记待裁定 sensitive；这些条目的正文不进入 projects。
3. `malformed` 非空：登记待裁定 malformed，附文件与原因；这些文件本次不更新 processed。
4. 「无项目工作」「会话记录不可读」「日结失败」条目：只记入 runs，供周总结统计，不登记待裁定。
5. `truncated` 为 true：只处理已给出的条目，runs 注明，下次继续。

## 第二步 归类

- `project_id` 在 INDEX 或 projects/ 下已存在：直接用。
- `project_is_new` 为 true，或 id 不存在：条目有下一步、阻塞或假设的，立即创建 `projects/<id>/`（STATUS 用模板，「目标」写条目里那句话），INDEX 加一行，状态 active，一句话列注「自动创建 <日期>」。不等确认。三样都没有的一次性事务不建新项目，按 `misc` 折叠，runs 记一行「<id> 归入 misc」。
- `misc` 是杂项：目录不存在就按上条创建，目标写「一次就做完的杂事」；STATUS「现状」只列最近 5 件事，每件一句；不登记 merge-suggest。
- 新 id 与已有项目疑似同一个（名称近似、MAP 目录相同、内容互相引用）：照常创建，同时登记待裁定 merge-suggest；PENDING「内容」列按 notify.md 写两个项目的人话解释与关系。用户回复合并后按 notify.md「合并执行」做，按段合并，不整份粘贴。
- INDEX 中状态为「未迁移」的项目第一次收到条目：建目录，状态改 active。
- `project_id` 为 null 且不是特殊条目：写入 `projects/_unsorted/<今天>.md`，登记待裁定 unsorted。

## 第三步 按项目折叠

### 幂等：来源键（失败重跑不重复）

- 每条 entry 的来源键是 `<file>#<idx>`，取自预处理 JSON 的 `file` 与 `idx`，例如 `inbox/work-mac/codex/2026-09-14.md#2`。
- 追加到 DECISIONS、HYPOTHESES、CORRECTIONS 的行，「来源」列写 `<机器/agent> · <来源键>`；LESSONS 条目的「来源」行、PREFERENCES 条目括号内、PENDING 行的「内容」列末尾，也都带上来源键。
- 追加任何一行之前，先在目标文件里搜索这个来源键：已经存在就跳过，不重复写。LESSONS 的「出现」计数同理，同一来源键只计一次。
- STATUS 整体重写，天然不重复；history 按标题行查重。
- 上一次汇总中途失败留下的半成品不需要清理：重跑时按来源键查重即可。processed.json 仍然只在全部成功后更新。


先读项目现有的 STATUS、DECISIONS、HYPOTHESES、LESSONS，再按下列规则重写或追加。

排序：同一来源同一天多条，最后一条代表该来源当天状态，前面的作为过程进 history。不同来源按时间排列，都参与折叠。

### STATUS.md（整体重写，≤60 行）

| 段 | 规则 |
|---|---|
| 目标 | 沿用旧值。只有条目写「目标变更」、新项目首条、或用户在 PENDING 的裁定才改 |
| 现状 | 用最新条目的「做了」更新；被覆盖的旧句删掉；保留 5 条以内 |
| 假设（待验证） | 只列 HYPOTHESES 里未回填且未到期的；到期未回填的标「待回填」 |
| 下一步 | 每个来源最新条目的「下一步」，注明来源与日期；不矛盾就并列；矛盾进「待你裁定」 |
| 阻塞 / 未解决 | 并集去重；条目写「已解除」或「做了」里有对应解决动作才移除 |
| 最近成果 | 新增条目的「产物」，最多 10 条 |
| 已更正（30 天） | 新增条目的「更正」；超过 30 天的挪进 history（CORRECTIONS 永久保留） |
| 待你裁定 | 本项目未处理的 D 项 id 与一句话 |
| 最近参与 | 按来源列最后日期 |

只写 inbox 条目里的事实。本次汇总自己的运行情况（处理了几条、生成了哪些文件、正在校验、此前汇总失败）不写进任何项目文件，只写 `_meta/runs/`。

frontmatter：`project`、`generated`（本次时间）、`sources`（本次用到的 inbox 文件）、`status`。超过 60 行：压缩「现状」「最近成果」，细节放 history；不删「已更正」「待你裁定」「阻塞」。

### DECISIONS.md（追加）

每条「决定」一行：`| 日期 | 决定 | 原因 | 未选 | 来源 | 状态 |`，状态「有效」。「更正」推翻了旧决定：旧行状态改「已推翻（见 <日期>）」，不删行。超过 50 行：最早 20 行压成「早期决策摘要」段，原行进 history。

### HYPOTHESES.md（追加与回填）

每条「假设」一行：`| id | 提出 | 假设 | 验证方法 | 到期 | 结果 | 归因 | 状态 |`，id 为 `H-<日期>-<序号>`（序号从 `ids.next.H` 起，全库唯一），到期缺省为提出日 + 30 天，状态「待验证」。

回填：新条目的「做了」「更正」「决定」提到某条假设的结果时，写入结果并按归因三分类处理：

| 归因 | 处理 |
|---|---|
| 路径本身错 | 状态「已推翻」，并在 CORRECTIONS 入档 |
| 执行走样 | 状态「执行偏离」，假设本身保留待重验 |
| 外部环境变 | 状态「环境变更」，保留待重验 |
| 预测正确 | 状态「已验证」 |

到期超过 30 天仍未回填：状态「过期」，保留不删。

### LESSONS.md（本项目）与 lessons/LESSONS.md（通用）

- 每条「经验」先在两处找同场景同做法的既有条目：有，只追加日期并把「出现」加一；无，新增，id `L-<日期>-<序号>`，带标签，状态「待验证」。
- 通用与项目专属：不依赖本项目具体的人、表、路径的放通用；拿不准放项目专属。
- 状态由结果决定：≥2 个不同日期的「产物」或「做了」证明做法有效 → 已验证；≥1 条「更正」推翻 → 需复核；被明确否定 → 已失效（保留）。
- 「skill 反馈」条目汇入 skills/REGISTRY.md 的「最近反馈」列（见 skills-lifecycle.md）。

### lessons/CORRECTIONS.md（偏差档案，追加）

每条「更正」一行：`| B-<日期>-<序号> | 日期 | 项目 | 场景 | 偏差 | 根因 | 修正 | 来源 |`；根因缺失写「未填」。用户指出的召回错误、归类错误也入档，场景写「召回失误」或「归类失误」。

### user/PREFERENCES.md

偏好只收以后都适用的话。新「偏好」先分档，再按来源等级分流，用户已经说过的话不再问一遍：

- 只管这一次的指令（「先帮我把目标写了」「这次新建一封邮件」）：不进 PREFERENCES。
- 某个项目的方案取舍（选 A 不选 B）：写成该项目 DECISIONS 一行，不进 PREFERENCES。
- 原话带「以后、后续、每次、所有、默认、一律、不要再、别再」或用户说了「记住」，且来源等级为「用户告知」：直接写进「已确认」段：`- [P-<日期>-<序号>] 「原话」（来源：用户原话 <日期>；范围：<全局 | 全局·哪类输出 | 项目 id>；<机器/agent> · 来源键）`，不登记待裁定。
- 其他（标为「推断」、没有信号词的长期习惯或项目口径、或来源等级行没有提到偏好）：进「待确认」段，同样格式但来源写「推断」。不登记待裁定、不通知，由周总结第 7 节集中列出，用户回「确认 P-…」或「作废 P-…」。
- 无论哪种，与「已确认」里现有偏好矛盾：不写入，登记待裁定 preference-conflict，内容里把新旧两句都引出来。
- 条目「更正」点名某些 P 编号作废、改范围或改成项目决定（来源等级为用户告知）：照做，不登记待裁定。改范围的只改原行「范围：」后的值；作废的从原段移到文件末尾「已作废」段（没有就建），行末注「〔作废 <日期>：原因 · 来源键〕」；改成项目决定的，在对应项目 DECISIONS 加一行（来源列注明「原 P-…」），原行同样移到「已作废」段并注明去向。

### history

本次涉及的条目原文追加到 `projects/<id>/history/<条目日期>.md`；追加前按标题行查重。

## 第四步 冲突判定

下列情况不自动裁决，写进 STATUS「待你裁定」和 `_meta/PENDING.md`：

1. 同项目两个来源对同一件事结论相反：完成与未完成、放弃与继续、产物指针不同。
2. 两条「更正」互相矛盾。
3. 新条目与 DECISIONS 中「有效」的决定相反，且没有写「更正」。
4. 「下一步」互相排斥。
5. 偏好冲突、合并建议、无法归类、疑似密钥、格式错误。

判定用内容，不用时间先后。

## 第五步 索引与收尾

1. 重建 `projects/INDEX.md`「## 项目」表：`| 项目 id | 一句话 | 状态 | 最近活动 | 参与 | 待裁定 |`，按最近活动倒序；保留状态为「未迁移」「done」「paused」「已停用」的行。预处理给出的 `status_changes` 逐个照做：INDEX「状态」列与该项目 STATUS frontmatter 的 `status` 一起改（只改这一行，不重写 STATUS 其他内容），不登记待裁定、不通知；runs 逐个列出项目、变化和原因。
2. 重建 `lessons/INDEX.md`：标签 → 经验 id；项目 → 经验数。
3. 满足 Skill 草案条件的经验：按 skills-lifecycle.md 起草。
4. 写 `_meta/runs/<今天>.md`：处理的文件、条目数、涉及项目、新建项目、新增待裁定、失败项、各机器各 agent 最近条目日期。
5. 回读本次写过的每个文件，确认可解析、STATUS 不超限。STATUS 首行必须是 `---`，frontmatter、`# 标题`、`## 段落` 一律顶格，不能有缩进；发现缩进就重写该文件。预处理 JSON 的 `status_format_errors` 列出的项目即使本次没有新条目也顺手修正，并在 runs 里记一行。
6. 全部成功后更新 `_meta/processed.json`：对 prep 输出 `files` 中的每个文件写 `{"hash": ..., "entries": ...}`（malformed 的文件除外）。任一写入失败：不更新 processed，runs 记失败项，按 notify.md 发 merge-failed。
7. 按 notify.md 写最终回复：第一行统计；本次新增的待裁定按五段式逐项列出；系统异常（merge-failed 等）同样列出；都没有就写「无待裁定」。
